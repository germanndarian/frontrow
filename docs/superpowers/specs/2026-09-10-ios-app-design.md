# Frontrow on iPhone — design

**Date:** 2026-09-10
**Status:** approved, pending implementation plan

## Goal

Put Frontrow on the maintainer's iPhone as an installed app with the same
functionality as the website, without removing or forking the website, without
the App Store, and without ongoing cost.

## Decisions taken

| Question | Decision |
| --- | --- |
| Phone | iPhone (iOS) |
| Packaging | Capacitor → native `.ipa`, installed via Xcode |
| Offline behaviour | None. Online-only; no service worker, no cached data |
| Sign-in inside the app | Email/password only. Google and GitHub hidden |
| Website | Unchanged in a browser. All app-specific behaviour is gated |

The maintainer chose Capacitor over an installable PWA with the 7-day
re-signing requirement made explicit beforehand.

## Architecture

The iOS app is a **native shell around a `WKWebView` that loads the live
production deployment**. It is not a copy of the site.

```
 iPhone ─▶ Frontrow.app (Capacitor/WKWebView)
              └─▶ https://frontrow-ten.vercel.app
                     └─▶ /api/* ─▶ ESPN  ·  Supabase auth (cookies)
```

### Why the site is not bundled into the app

Bundling was considered and rejected. The pages are statically rendered, but
the dashboard depends on `/api/*` route handlers that proxy ESPN server-side,
and authentication is cookie-based through `@supabase/ssr`. A bundled frontend
calling the API from `capacitor://localhost` would be a cross-origin request,
requiring CORS on every route and cross-site cookies for auth — which browsers
increasingly refuse. Loading the deployed origin directly keeps auth, cookies
and the API exactly as they are on the web.

A consequence worth stating plainly: **the 7-day signing expiry applies to the
shell, not the content.** Content and data changes ship from Vercel and appear
in the app on next launch with no rebuild. Only the app binary expires.

## Components

### 1. Capacitor project

Dev dependencies: `@capacitor/core`, `@capacitor/cli`, `@capacitor/ios`.

`capacitor.config.ts` at the repo root:

- `appId: "com.germanndarian.frontrow"`
- `appName: "Frontrow"`
- `server.url` → the production deployment
- `webDir` → `capacitor/www` (see below)

### 2. Offline fallback page

Capacitor requires a valid `webDir` even when `server.url` is set. A minimal
`capacitor/www/index.html` fills that role and doubles as the screen shown when
the phone cannot reach the deployment — a branded "can't reach Frontrow"
message instead of a raw WebKit error. It is static HTML with inline styles; it
does not import from `src/`.

### 3. App icon

`public/stadium-logo.png` is 1408×768 with an alpha channel. iOS requires
1024×1024, square, fully opaque. The icon is generated by centre-cropping to
square (matching the `object-cover` crop `Wordmark.tsx` already applies),
scaling to 1024×1024, and flattening transparency onto `#f1f1ec` — the light
background already used as `themeColor` in `layout.tsx`. If review shows the
mark reads poorly on light, the dark palette's background is the fallback.

The generated icon is reviewed by the maintainer before it is committed.

### 4. Xcode project

`ios/` is generated by `npx cap add ios` and committed, so signing
configuration and icon assets survive. Gitignored within it: `Pods/`, `build/`,
`DerivedData/`, `xcuserdata/`.

### 5. Web-app changes

All three are small and must leave browser behaviour identical.

**Safe areas.** Add `viewportFit: "cover"` to the existing `viewport` export in
`src/app/layout.tsx`, and safe-area padding in `globals.css` so the header
clears the notch and content clears the home indicator. Without this the header
renders underneath the status bar.

**Native detection.** A `useIsNativeApp()` hook reading the `window.Capacitor`
global that the native runtime injects. It follows the existing
`useHasHydrated` pattern so the first client render matches the server render
and no hydration mismatch occurs. No new runtime dependency enters the website
bundle — the hook is a `typeof window` check.

**Login page.** Hide the Google and GitHub buttons when `useIsNativeApp()` is
true, leaving email/password. Google refuses OAuth from embedded WebViews
(`disallowed_useragent`), so those buttons would fail rather than degrade. The
website keeps all three methods.

## Data flow

Unchanged from the website. The WebView is a browser: same origin, same
cookies, same `/api/*` routes, same React Query caching. No new data path is
introduced, which is what makes "identical functionality" true by construction
rather than by effort.

## Error handling

| Condition | Behaviour |
| --- | --- |
| No network at launch | `capacitor/www/index.html` fallback screen |
| Network lost mid-session | Existing in-app error and stale states apply |
| ESPN upstream failure | Existing `ErrorState` / `StaleNotice` (PRs #26, #27) |
| Signing certificate expired | App refuses to launch; re-sign from Xcode |

No new error-handling code is introduced beyond the fallback page.

## Testing

- `npm run lint`, `npx tsc --noEmit`, `npm test`, `npm run build` must stay
  green. `capacitor.config.ts` at the root must not break the TS project, and
  `ios/` must be excluded from lint and type-check.
- Unit test for `useIsNativeApp()` covering both the browser case (no
  `window.Capacitor`) and the native case.
- Manual verification on the physical device: launch, log in with email and
  password, dashboard renders live scores, settings and setup reachable,
  header clears the notch, content clears the home indicator, OAuth buttons
  absent.
- Manual verification in a browser that the login page is unchanged and still
  offers all three sign-in methods.

## Build and install procedure

1. `npm run ios:sync` → `npx cap sync ios`
2. `npm run ios:open` → `npx cap open ios`
3. In Xcode: select the project, set Signing Team to the personal Apple ID.
4. Connect the iPhone, select it as the run destination, press Run.
5. On the iPhone: Settings → General → VPN & Device Management → trust the
   developer certificate.
6. **Every 7 days:** reconnect and press Run again.

Free provisioning limits: 7-day certificates, 3 sideloaded apps installed at
once, 10 new app IDs per week.

## Risks and constraints

- **The 7-day expiry is permanent** under free provisioning. The only removal
  is the $99/yr Apple Developer Program.
- **The app mirrors production.** It shows whatever the deployed site shows.
- **Google OAuth cannot work in a WebView.** Handled by hiding the buttons; a
  future `ASWebAuthenticationSession` flow could restore them.
- **No browser back button.** In full-screen the only navigation is in-app.
  The header's Home button logs the user out by design (PR #23), so in the app
  the sole exit from the dashboard is a logout. Behaviour is left unchanged;
  flagged for a future decision.

## Out of scope

Push notifications, home-screen widgets, background refresh, offline data,
Android, App Store distribution, and any change to the website's own
functionality.

## Addendum (2026-09-11): the 1b app UI

After the shell shipped, the maintainer designed a native-feeling UI in
Claude Design ("Frontrow mobile app redesign", option **1b**) and chose it
over the web layout in a frame. Decisions taken when implementing it:

- **Own route, not a gate.** The app UI lives at `/app`; the shell's
  `server.url` points there. The website's routes are byte-identical in a
  browser — nothing in `/dashboard`, `/login` or `/settings` changed.
- **Presentation layer only.** Every screen reads the existing hooks and
  stores (`useScoreboard`, `useTeamSlate`, `useTeamCard`, `usePlayer`,
  `useStandings`, `usePlayoffBracket`, `useSchedule`, `usePreferences`,
  `useSettings`, `useAuth`). No new API routes, no new data paths.
- **Screens.** Welcome → Login (email/password + guest; no OAuth, per the
  earlier decision) → Setup (the existing `SetupFlow`, given `after`,
  `onDone` and `seedFromStore` props) → five tabs: Scores, Teams, Players,
  Table, Settings. Sheets for schedule, bracket and player detail.
- **Staying signed in** is a consequence of the navigation: there is no Home
  button, and Sign out lives only in Settings. Sessions already persisted;
  the web header's Home-logs-out behaviour was what ended them.
- **Deferred.** The onboarding screen still uses the web `SetupFlow`
  styling rather than the mockup's; the welcome screen omits the mockup's
  sample live-game card (it was placeholder data).

## Addendum (2026-09-11): onboarding to the mockups; system theme

- **Onboarding** now follows the design's turns 2 and 3: a fixed header
  with the step rail, tappable rows with a 44px mark and a 24px check, a
  fixed footer with back / count / action, and a new **Done** screen
  (summary of picks, live-game count, "Go to my dashboard" / "Add more
  teams"). `SetupFlow` is shared, so `/setup` on the website gets the same
  look, laid out as a centred column on desktop. Onboarding is marked
  complete only when the user leaves Done, so `/app`'s gate can't swap the
  screen out early; picks are saved on Finish regardless.
- **Theme** gains a **System** option, the default for new accounts
  (`0003_appearance_system.sql` changes the column default; run it in the
  SQL Editor). Light/dark choices persist as before. A first-paint script
  in `layout.tsx` applies the remembered choice — or the device scheme —
  before React loads, so nothing flashes.
- Out of scope, by instruction: the home-screen frame in turn 3 and its
  app-icon asset. Not done yet: the tab-bar icons added to turn 1.
